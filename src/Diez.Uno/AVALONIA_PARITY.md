# Avalonia → Uno Platform — functional parity inventory

This file is the migration checklist for the Uno frontend. The repository and `PROJECT_STATE.md`
are the source of truth; chat history is not used as a regression baseline.

## Migration rules

- PR #37 remains open, draft and unmerged.
- The Uno work stays on `spike/uno-platform-ui`.
- No Avalonia layout pump, `RedrawWindow`, compositor reflection, root swapping or manual template recovery is allowed in Uno.
- Home and every workspace live under one permanent Uno shell.
- `.diez` data must be preserved. The Uno document adapter rewrites `project.json` without deleting unknown JSON sections and copies existing embedded ZIP entries forward.
- Scene IDs are stable and never regenerated by rename/edit.
- Prompt/Vision HARD constraints remain visible and must not be weakened.

## Current Uno implementation status

The Uno shell now exposes every major functional area above in one permanent visual tree and persists its migration state into `UnoUiState` inside `project.json`. Existing project sections are preserved untouched unless Uno explicitly edits a compatible field such as project name, edition title, book type, materials or AI jobs.

Deep domain engines that are still physically mixed with Avalonia types in the current source tree must be extracted into a UI-neutral `Diez.Core` layer before Uno can call them directly. The Uno UI therefore labels those operations explicitly instead of pretending the old Avalonia `*Ui.cs` modules are being reused.

The next migration layer is service extraction, in this order:

1. project/material/content graph/editable master/consistency;
2. book-type profiles, structured subjects/scenes and Prompt Compiler;
3. Word Search and Crossword services;
4. AI Exchange/Production/Prompt Pack/Vision;
5. DOCX/Google/finalization services.

The visual layer must not be rewritten again while those services are extracted.
